# Граждански контрол

Приложение за въпроси и отговори с разширено извличане (RAG) върху стенограмите
от пленарните заседания на Народното събрание на България. Питайте какво е било
казано в пленарната зала и получете кратък, обоснован отговор, който цитира
точните изказвания, от които произлиза (`[S#]`) — всяко твърдение препраща към
оригиналния запис.

Извличането работи локално върху [LanceDB](https://lancedb.com/) индекс (плътни
`BAAI/bge-m3` вектори + BM25, обединени и преподредени с cross-encoder).
Генерирането използва произволен LLM, съвместим с OpenAI. Бекендът е на Python /
FastAPI (поточно предаване чрез SSE); фронтендът е на Next.js.

Състои се от три части:

- **Постъпване на данни (Ingestion)** — изтегля стенограмите от parliament.bg и изгражда индекса за търсене.
- **Бекенд** — услуга на FastAPI, която обслужва API върху този индекс.
- **Фронтенд** — чат интерфейс на Next.js.

Постъпването на данни и бекендът споделят една Python среда в `backend/`.

## Предпоставки

- **Python ≥ 3.10** с [`uv`](https://docs.astral.sh/uv/) — за постъпването на данни и бекенда.
- **Node.js** с [`pnpm`](https://pnpm.io/) — за фронтенда.
- **API ключ за LLM, съвместим с OpenAI** — необходим само за генериране на
  отговори; извличането и вгражданията (embeddings) работят локално без ключ.

## 1. Постъпване на данни — изграждане на индекса

```bash
cd backend
uv sync                       # инсталира зависимостите в .venv
cp .env.example .env          # задайте OPENROUTER_API_KEY (вижте "LLM доставчик" по-долу)

# Изтегляне и индексиране на месец заседания (изберете произволен селектор на дата):
uv run python -m parl_rag.cli ingest --year 2026 --month 6
```

При първото изпълнение се изтегля моделът за вграждане (`bge-m3`, ~2.3 GB) от
Hugging Face и се кешира. Повторното изпълнение е безопасно — всяко заседание се
обновява по id, така че датите се заменят, а не дублират. Други селектори:
`--date 2026-06-11` (един ден), `--since 2026-04 --until 2026-06` (диапазон).
Пълна справка в [`backend/INGESTION.md`](backend/INGESTION.md).

## 2. Бекенд — API-то

От `backend/` (същата среда като при постъпването на данни):

```bash
uv run uvicorn parl_rag.api.main:app --host 127.0.0.1 --port 8077
```

Обслужва API-то на `http://127.0.0.1:8077` (Swagger UI на `/docs`). Повече в
[`backend/API.md`](backend/API.md).

## 3. Фронтенд — интерфейсът

```bash
cd frontend
pnpm install
pnpm dev                      # http://localhost:3000
```

## Стартиране с Docker

`docker-compose.yml` стартира двете услуги заедно. Бекендът чете LanceDB индекса
от `./data` (монтиран чрез bind), а кешира тегла на моделите на именуван том
(volume); фронтендът препраща `/api/*` към бекенда през compose мрежата.

```bash
cp backend/.env.example backend/.env   # задайте OPENROUTER_API_KEY
# Първо изградете индекса (на хоста или в контейнера) — вижте backend/INGESTION.md.
docker compose up --build
```

Интерфейсът е на `http://localhost:3000`, API-то на `http://localhost:8077`.

Бележки:

- **Моделите** (`bge-m3` + преподредителя, ~5 GB) се изтеглят при първото
  стартиране в тома `hf_cache`, затова проверката за здраве (healthcheck) на
  бекенда има дълъг `start_period`. Следващите стартирания са бързи.
- **Данните** се намират в `./data` на хоста, монтирани чрез bind в бекенда, така
  че изграденият индекс се запазва и се прихваща автоматично от API-то.

### Постъпване на данни в Docker

CLI инструментът за постъпване на данни работи вътре в контейнера на бекенда — не
се подават пътища или ключове, тъй като монтирането на `./data`, томът с модели
`hf_cache` и `backend/.env` вече са свързани от `docker-compose.yml`. Изберете
формата, който отговаря на състоянието ви:

```bash
# Стекът вече работи (docker compose up) — изпълнете вътре в живия контейнер:
docker compose exec backend python -m parl_rag.cli ingest --year 2026 --month 6

# Стекът е спрян — изпълнете еднократен контейнер, който се самопочиства:
docker compose run --rm backend python -m parl_rag.cli ingest --year 2026 --month 6
```

Другите селектори работят по същия начин: `--date 2026-06-11` (един ден),
`--since 2026-04 --until 2026-06` (диапазон), `--skip-existing` за пропускане на
дни, които вече са на диска. Първото изпълнение е бавно (изтегля модела за
вграждане, вгражда всеки фрагмент и прави LLM заявки за контекстуалната стъпка);
по-късните изпълнения преизползват кеширания модел и вграждат отново само
променените заседания. Пълна справка в [`backend/INGESTION.md`](backend/INGESTION.md).

## LLM доставчик — произволен API, съвместим с OpenAI

Генерирането на отговори използва `openai` SDK срещу произволна крайна точка,
съвместима с OpenAI, така че смяната на доставчик е само въпрос на конфигурация —
без промени в кода. Работи с OpenRouter (по подразбиране), OpenAI, Groq,
DeepSeek, локален Ollama / LM Studio сървър или всичко друго, което говори OpenAI
API.

Задайте три променливи в `backend/.env`:

| Променлива | Какво представлява |
|---|---|
| `OPENROUTER_API_KEY` | API ключ за вашия доставчик. Променливите носят името на OpenRouter, който е по подразбиране, но важат за която и да е зададена крайна точка. Задължителен е за OpenRouter; локален сървър без ключ може да го остави празен. |
| `OPENROUTER_BASE_URL` | Базовият URL, съвместим с OpenAI. По подразбиране е OpenRouter; напр. `https://api.openai.com/v1` или `http://localhost:11434/v1` за Ollama. |
| `PARL_LLM_MODEL` | Идентификаторът на модела, който да се използва, както е наименуван от съответния доставчик (напр. `openai/gpt-5`, `gpt-4o`, `deepseek/deepseek-chat`). |

Вижте [`backend/.env.example`](backend/.env.example) за всички опции, включително
по-евтините модели, използвани за контекстуалната стъпка при постъпване на данни
и за проверката за наличие на отговор (answerability gate).
